# Uvance AIOps 客戶提案草稿：HPC/AI 叢集多代理故障診斷

> **內部草稿，非正式對外文件。** 內容依本 PoC 的實際成果撰寫，不含市場規模、價格或客戶名稱。
> 對外使用前需經業務、法務與品牌審查。凡標示「尚未驗證」的項目，不得作為對客戶的承諾。

## 1. 提案摘要

HPC 與 GPU 叢集的故障常常同時牽涉網路、儲存、排程與 GPU 多個層面，工程師必須在多套系統之間來回查證，才能定位根本原因。

本方案由多個專責 Agent 協作完成根因分析：

- **分流 Agent**：判斷故障屬於哪些領域，交給對應的診斷 Agent。
- **診斷 Agent**：分別負責儲存、排程、網路、GPU，透過唯讀工具收集證據。
- **RCA 協調者**：把各領域的發現與時間軸串連起來，排序可能原因。
- **處置 Agent**：依 SOP 劇本提出處置計畫，附執行前驗證、回復方式與參考 SOP。

所有處置都必須經過**人工核准**，而且系統本身**不執行任何動作**。這在追求維運效率的同時，確保操作安全。

## 2. 客戶面臨的問題

- 跨層故障（例如節點 DRAIN、作業被 SIGKILL、網路鏈路中斷同時發生）需要多個團隊交叉比對，定位耗時。
- 資深工程師的判斷經驗分散在個人身上，SOP 與過去事件難以在處理當下即時取用。
- 直接讓 AI 自動修復正式環境，風險不可接受；必須可追溯、可稽核，並由人做最後決定。
- 多個據點之間的作法與門檻不一致，經驗難以複製。

## 3. 方案內容（PoC 已實作）

| 能力 | 內容 |
|---|---|
| 多 Agent 協作 | 以 Microsoft Agent Framework 編排：分流 → 儲存／排程／網路／GPU 診斷 → RCA 協調者 → 處置 Agent |
| 證據可追溯 | 事實、假設、已排除原因、缺少的資訊明確區分；每項證據都標示來源 |
| 拒絕無根據的結論 | 證據不足時只提出假設與建議檢查，不宣稱根本原因；評估中的無根據主張率為 0% |
| 處置計畫 | 只對「有工具證據、且信心度達到據點門檻」的假設提出；其餘列出暫緩原因 |
| 人工核准 | 核准、退回、要求修改；AI 身分無法核准；核准只記錄、不執行 |
| 稽核 | 雜湊鏈不可竄改紀錄，涵蓋診斷、決定與 AI 說明 |
| 地端部署 | 單一容器、非 root、唯讀檔案系統、只綁本機；可完全離線運作 |
| 可選本機 LLM | 透過 Ollama 用本機模型產生繁體中文說明，有嚴格的證據檢查，不連雲端 |
| 模組化推廣 | 據點設定檔調整門檻，但無法放寬安全規則；跨據點指標定義一致 |
| 離線資料匯入 | 由人匯出的 CSV 經資料契約驗證、主機／作業／檔案系統名稱假名化後匯入；含 IP、Email、網域或憑證的事件整筆拒收；系統不連線任何來源 |
| 繁體中文介面 | 審查網頁全中文化 |

## 4. 差異化

1. **安全優先，而非自動修復。** 處置只提案、不執行；工具採白名單、預設拒絕；整個系統沒有任何 shell 或遠端執行能力。
2. **證據導向，可拒絕下結論。** 評估案例中，該拒絕下結論的都正確拒絕。
3. **適合封閉環境。** 支援離線、地端與本機模型，適合研究、氣象等對資料外流敏感的 HPC 單位。
4. **可複製。** 據點只調整門檻、資料轉接與知識庫，核心邏輯與安全機制不分叉。

## 5. 提供形式（候選，待業務評估）

- **地端軟體授權與導入服務：** 容器映像、據點設定、資料轉接器開發、知識庫整理。
- **整合服務：** 與客戶既有的監控系統、排程系統（PJM／Slurm）、FEFS／Lustre 及 DCGM 匯出資料進行唯讀整合。
- **維運支援：** 持續更新處置劇本與評估案例，提供定期的成效量測報告。

## 6. 導入路徑

| 階段 | 內容 | 完成條件 |
|---|---|---|
| PoC（已完成） | 合成資料、三個情境、安全機制、人工核准、評估工具、容器 | 測試全數通過，評估中無根據主張率為 0% |

## 7. 實證狀態（如實揭露）

**已驗證（PoC，合成資料）：**
- 13 個評估案例中，分類準確率 100%、首位假設準確率 100%、無根據主張率 0%。其中分類規則曾在看過結果後調整，詳見評估報告的揭露段落。
- 證據不足的案例全部正確拒絕下結論。
- 容器安全檢查 17 項全數通過。

**尚未驗證（不得對外承諾）：**
- **故障定位時間或 MTTR 的縮短幅度。** 需依 [business-impact.md](business-impact.md) 的量測方案取得前後對照數據。
- 在真實事件上的準確率。目前的評估案例是合成資料，由開發者自行標註。
- 大規模資料下的效能、與正式系統的整合、SSO 與 TLS。
- 「AI 推理」能力。目前的診斷 Agent 是規則式軟體 Agent；本機 3B 模型只負責說明，實測通過率為 3 個中 1 個。要讓 LLM 參與推理，建議使用 7B 以上的模型並配備 GPU。

## 8. 客戶需提供

- 去識別化的歷史事件與處理紀錄，以及能標註根本原因的工程師。
- 唯讀的資料匯出（排程、儲存、網路、GPU）與 SOP 文件。
- 工單系統的時間戳記，用來建立 MTTR 基準。
- 安全審查窗口與部署環境（地端主機，若要使用本機 LLM 則需要 GPU）。

## 9. 風險與對策

| 風險 | 對策 |
|---|---|
| 客戶期待全自動修復 | 明確定位為「AI 提案、人做決定」；把核准紀錄當成合規優勢來說明 |
| 小模型品質不足 | 規則式診斷為主、LLM 為輔，並以證據檢查擋下錯誤說明；試點評估更大的模型 |
| 成效無法證明 | 試點一開始就依量測方案收集基準數據 |
| 各據點各自修改、失去一致性 | 只允許調整設定檔；核心程式單一版本，依映像標籤升級 |
