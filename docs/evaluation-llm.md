## What this shows

- **The checks hold.** Every kept proposal cites a tool value the agent actually fetched or an incident
  item; evidence statements are written from the data; proposals backed only by incident reports are
  capped at confidence 0.3; nothing was confirmed; no agent fell back to the rules; both current runs
  have 0 unsupported claims under the harness definition. An earlier 3B run produced two *grounded but
  wrong* claims (a real `used_pct=83` cited as a capacity problem): the checks verify that evidence
  exists, not that the reasoning about it is right; that remains the reviewer's job.
- **The results are unstable.** After the site thresholds were added, 7B's correct refusal rose from 0%
  to 67% and every open hypothesis was tool-backed, but top-1 fell from 55% to 36%. One of the flipped
  refusals (EVAL-UNK-001) has no relevant threshold, and the 3B model has swung between 36% and 55% top-1
  on similar small changes. With 13 cases and models this small, the gain in refusal can't be
  attributed to the thresholds, and these runs do not show that any change improved reasoning overall.
- **The GPU regression is the checker again.** Re-running POC-GPU-001 with 7B on the current code shows
  the GPU agent's proposal discarded because it cited `where: "sim-gpu-node-0007 GPU 3"`: the value is in
  the data, but the matcher only skips context *key names* (`node`, `index`) inside a compound ID, and
  `GPU` is not one. This is reported here, not fixed, because it was found on these cases; fixing it
  needs another disclosed re-run. Both GPU cases' top-1 misses in the current 7B run are likely this.
- **Same code, 3B vs 7B.** The current columns are the first like-for-like comparison. Top-1 is a tie
  (36% and 36%); 7B is ahead on correct refusal (67% against 33%), outcome (77% against 54%),
  tool-backed hypotheses (100% against 50%) and discarded proposals (5 against 25). Every 3B confidence
  is 0.10: the model gave no usable confidence, and the code applied its 0.1 default. 7B follows the
  protocol better; it does not pick the root cause better.
- **The models reason worse than the rules on these cases.** Neither reports domain-specific missing
  information (0%), and both lead with the wrong category in several scheduler and storage cases.
- **The comparison favours the rules.** These cases were written together with the rule-based agents, so
  the rules scoring 100% is expected. Representative, independently labelled incidents are needed to
  compare fairly.
- **Speed.** About 1 minute (3B) to 3 minutes (7B) per diagnosis on this CPU, against milliseconds for the
  rules.

## Skills (2026-11-10)

- Adding four skills, read on demand with `load_skill`, did not improve the 7B results: top-1 stayed at
  36%, correct refusal fell from 67% to 33%, and one unsupported claim appeared (EVAL-STOR-003 led with
  `storage.capacity`). Within the run-to-run spread seen above, this is no measurable change.
- A traced 7B run on POC-SCHEDULER-001 shows why: the scheduler agent never called `load_skill`. It
  used `search_manual` and `search_sop` instead. On-demand skills (the Claude Code pattern: an index in
  the prompt, full text when needed) rely on the model deciding to read them, which this model does not.
- EVAL-SCHED-001 still led with `scheduler.signal_termination` although the scheduler skill states how
  to compare `elapsed` with `requested_walltime`; the model had not read it.
- Not changed after seeing this: preloading the relevant skill into small models' prompts is a design
  option, but it would be a change made on these cases and must be disclosed and re-run if applied.

## Next steps

- A larger model is the next real test, not more prompt changes on these 13 cases. qwen2.5:14b needs
  roughly 10 GB of memory with an 8k context; this host has about 6 GB available, so it was not tried here.
  It should run on a host with a GPU or more memory, still on premises (Ollama).
- More cases, labelled independently, and several seeds per case, to measure the spread instead of
  reading single runs.

## Recommendation

Keep the LLM-driven agents opt-in (`HPC_AGENT_REASONING=llm`) and the rule-based agents as the default for
review work until a larger model beats the rules on independently labelled incidents.

### Disclosure: changes made after seeing these results

- **2026-10-21: RCA classification rule.** The first evaluation run classified EVAL-STOR-001 and EVAL-STOR-003 as `multi-domain`. Each is a single-symptom write failure ("job failed while writing…") where keyword triage tied storage with the scheduler, although only storage had tool evidence. Domain classification was then **85% (11/13)**. The rule was changed so that when tool-backed hypotheses span exactly one domain, the RCA uses that domain. Classification results on these 13 cases after that change are **not** an independent test of the rule; new, independently labelled cases are needed for that.
- **2026-10-22: LLM specialist prompt and fact parsing.** After one qwen2.5:3b run on POC-SCHEDULER-001 (one of these cases), in which the model called only knowledge tools and put incident items (I#) under tool facts, the prompt was changed to name the agent's data tools and ask for them first, and an I# under facts is now treated as a reported item instead of discarding the proposal. A line telling the model that incident text is data, not instructions, was added before the qwen2.5:7b run. The prompt and checks were then frozen; mismatches are reported, not tuned away.
- **2026-10-22: scheduler category list.** The LLM scheduler agent's category list first omitted `application.crash` and `application.exit_code`, which the rule-based scheduler agent uses. The omission was noticed in the rule-based report and fixed before the runs reported here.
- **2026-10-23: fact matcher.** Re-running POC-GPU-001 with qwen2.5:7b showed a grounded proposal discarded because it cited `field: "xid_events.count"` with `where: "sim-gpu-node-0007:3"`, while the matcher accepted only a leaf name and a single record ID. The matcher now also accepts a dotted path that ends at the cited field (list indices ignored) and a compound ID whose every part identifies the record. The value must still match the data exactly. This was found on these cases, so results after it are not an independent test of it.
- **2026-10-26: site thresholds in the specialist prompt.** After the 7B rerun, EVAL-STOR-002 showed the model calling a 55-61% OST spread an imbalance; the rule-based agents apply the site profile's thresholds, which the LLM agents had not been given. The specialist prompt now states the site profile's thresholds for its domain (storage full and OST spread, GPU thermal limit), the same values the rules use. No case-specific hints were added. This was found on these cases, so results after it are not an independent test of it.

### Method

- Cases live in `evaluation/cases/`. Each case runs through the full workflow (triage,
  specialists, RCA Coordinator, runtime guard) in an isolated temporary data root.
- **Outcome** is `supported_hypothesis` when the leading open hypothesis has tool evidence,
  `insufficient_evidence` when it rests only on reported symptoms, and
  `no_supported_hypothesis` when nothing is open.
- **Unsupported claims** are confirmed causes, open hypotheses with confidence of at least
  0.5 and no tool evidence, and hypotheses in a case's forbidden categories.
- **Human override rate** counts REJECTED and REVISION_REQUESTED among recorded human
  decisions (`--approvals-log`). It is never simulated.
- **Next step toward a real evaluation:** representative, de-identified incidents labelled
  independently by operations engineers, plus override rates from real reviews.
