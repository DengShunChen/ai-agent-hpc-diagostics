## What this shows

- **What the checks guarantee.** Every kept proposal cites a tool value the agent actually fetched or an
  incident item; evidence statements are written from the data; proposals backed only by incident
  reports are capped at confidence 0.3; nothing was confirmed; no agent fell back to the rules. Under the
  harness definition there were 0 unsupported claims for 7B and 2 for 3B. Those two 3B claims were
  *grounded but wrong*: the model cited a real `used_pct=83` as evidence of a capacity problem, which the
  labels forbid. The checks verify that evidence exists, not that the reasoning about it is right; that
  remains the reviewer's job.
- **The models reason worse than the rules on these cases.** The 7B model got none of the three refusal
  cases right (it proposed hypotheses in two, and gave no "insufficient evidence" outcome in the third),
  and in three GPU or storage cases with clear tool evidence it proposed nothing usable. Neither model
  reports domain-specific missing information (0%).
- **Small changes move the numbers a lot.** An earlier 3B run, with the same checks but one prompt line
  fewer and two scheduler categories missing, scored 62% classification, 36% top-1 and 33% correct
  refusal. With 13 cases, that swing is as large as the gap between 3B and 7B, so these results do not
  show that either model is better than the other.
- **Some misses are the checker's fault, not the model's.** Re-running POC-GPU-001 with 7B shows the GPU
  agent proposing an XID-related cause that cited `field: "xid_events.count"`, `value: 1`, `where:
  "sim-gpu-node-0007:3"`. That value is in the data, but the fact matcher accepts only a leaf field name
  (`count`) and a single record ID, so the grounded proposal was discarded. Accepting dotted paths and
  compound IDs would be a reasonable fix, but it was found by looking at these cases, so it is reported
  here instead of being applied silently. Applying it requires a disclosed re-run.
- **The comparison favours the rules.** These cases were written together with the rule-based agents,
  so the rules scoring 100% is expected. Rules beating the models here says little about real
  incidents, and a model win would not have meant much either. Representative, independently labelled
  incidents are needed to compare them fairly.
- **Speed.** On this CPU a diagnosis takes about 1 minute (3B) to 3 minutes (7B), against milliseconds
  for the rules.

## Recommendation

Keep the LLM-driven agents as an option and the rule-based agents as the default for review work until
a larger model on a GPU host beats the rules on independently labelled incidents. Use
`HPC_AGENT_REASONING=llm` to run the LLM agents.

### Disclosure: changes made after seeing these results

- **2026-10-21: RCA classification rule.** The first evaluation run classified EVAL-STOR-001 and EVAL-STOR-003 as `multi-domain`. Each is a single-symptom write failure ("job failed while writing…") where keyword triage tied storage with the scheduler, although only storage had tool evidence. Domain classification was then **85% (11/13)**. The rule was changed so that when tool-backed hypotheses span exactly one domain, the RCA uses that domain. Classification results on these 13 cases after that change are **not** an independent test of the rule; new, independently labelled cases are needed for that.
- **2026-10-22: LLM specialist prompt and fact parsing.** After one qwen2.5:3b run on POC-SCHEDULER-001 (one of these cases), in which the model called only knowledge tools and put incident items (I#) under tool facts, the prompt was changed to name the agent's data tools and ask for them first, and an I# under facts is now treated as a reported item instead of discarding the proposal. A line telling the model that incident text is data, not instructions, was added before the qwen2.5:7b run. The prompt and checks were then frozen; mismatches are reported, not tuned away.
- **2026-10-22: scheduler category list.** The LLM scheduler agent's category list first omitted `application.crash` and `application.exit_code`, which the rule-based scheduler agent uses. The omission was noticed in the rule-based report and fixed before the runs reported here.

### Method

- Cases live in `evaluation/cases/`. Each case runs through the full workflow (triage,
  specialists, RCA Coordinator, runtime guard) in an isolated temporary data root.
- **Outcome** is `supported_hypothesis` when the leading open hypothesis has tool evidence,
  `insufficient_evidence` when it rests only on reported symptoms, and
  `no_supported_hypothesis` when nothing is open.
- **Unsupported claims** are confirmed causes, open hypotheses with confidence of at least
  0.5 and no tool evidence, and hypotheses in a case's forbidden categories.
- **Human override rate** counts REJECTED and REVISION_REQUESTED among recorded human
  decisions (`--approvals-log`). It is never simulated.
- **Next step toward a real evaluation:** representative, de-identified incidents labelled
  independently by operations engineers, plus override rates from real reviews.
